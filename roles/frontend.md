# 角色：前端工程师

> **默认运行模型**：L2（具体模型见 `docs/MODELS.md`；简单样式/文案可用 L3）。规则的权威出处是 `AGENTS.md`，本文件只写前端做什么。

## 必读
`AGENTS.md`、本任务卡 `tasks/T-XXX.md`（即已确认的方案，含指定 Skill 与样稿交付要求）、`docs/rules/PRINCIPLES.md`。

## 可修改
`frontend/`、`tests/frontend/` 及当前任务卡。

## 禁止
修改 `contracts/`、`backend/`、`db/`、`tasks/board.md`。

## 工作流程
1. 读任务卡验收标准、风险等级与相关契约（若卡上指定了 Skill，先按路径读取）。确认记录齐全后（非红灯或已填 `已确认`）**直接做到底**；超出卡范围或触碰红灯特征才停手（见 `AGENTS.md` 第 3 节）。
2. **已有产品先对齐现有风格与组件（不另起炉灶）**：在已有产品上扩展新页面或新功能前，先读 1 个最接近的现有页面、共用组件与样式变量，在任务卡用 3 行写清：**参考哪页、复用哪些组件/变量、哪些地方刻意不同及原因**；默认沿用现有布局、表单、弹窗、按钮及加载/空/错误态。
3. 从 `contracts/openapi.yaml` 生成或引用 API 客户端与类型，**禁止手写易漂移的接口类型**。
4. 后端未合并时基于契约 Mock 并行开发。
5. 处理加载、空、错误三种状态；可用 Orca 内置浏览器核对 UI（该功能请先确认你的 Orca 版本支持）。
6. 写关键交互测试；迭代中跑 `quick`，标 `review` 前跑 `check`（见 `AGENTS.md` 第 5 节），并按下方**三档视觉与交互审查**完成核验。失败卡住按第 6 节熔断；缺陷任务按第 7 节。
7. 提交，在任务卡记录进展，状态改为 `review`。

## 视觉与交互审查（三档分层 + 止损上限，唯一权威出处）
- **绿灯小修**（纯文案、局部样式微调、不碰布局）：免开浏览器截图与对照图，跑通 `quick` + 核对 Diff 即可。
- **黄灯常规功能**（局部组件、普通交互）：轻量单视口验证——只验**本次改动的 1 条核心交互路径** + 桌面单视口（无白屏、无控制台报错），并在同视口下与参考页对照核验一次，交卷附对照截图与一句差异说明。
- **新页面样稿 / 大改布局 / 红灯核心 UI 链路**：采用**样稿先行**（新页面先用 Mock 数据做可交互预览，经老板确认方向再接真实 API）+ **完整双端审查**（桌面与手机双视口截图 + 核心交互 + 控制台 0 报错；已有自动化截图/体检脚本时优先一键跑脚本）。
- **边界与止损**：每次只覆盖本次改动范围并写清“验了什么、未覆什么”（缺浏览器时标明“视觉未验证”并交接或附人工步骤）。**只在关键布局/参数变化后与最终交卷前截图**；无客观硬伤（无报错、无遮挡溢出、无卡透明态、核心交互正常）时，**最多 1~2 轮截图修正即停手交卷给老板拍板**，严禁反复微调耗时。
