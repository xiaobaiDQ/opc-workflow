# OPC 工作流演进与交接手册

本手册归纳工作流搭建、真实任务试跑、独立审查以及专科扩展中验证过的取舍。执行以[项目规则](../AGENTS.md)、[进化官职责](../roles/evolver.md)和当前批准为准。审查时可用[审查指南](EVOLVER-REVIEW.md)逐步取证。

## 做判断的五条原则

1. **单一事实来源**。项目规则和任务卡承载生效要求；聊天可用于回放原始需求和纠偏过程。角色文档只写角色职责。
2. **模型档位与任务风险独立**。模型档位管成本与能力，风险等级管权限、审批与回滚。高风险方案由适当角色审清并获批后，执行仍可交给适合的编码模型。
3. **隔离母版、项目和 Bot**。母版存共用规则，项目适配实际工具、目录、分支和安全约束，Bot 存协作入口和项目记忆索引。
4. **可重复的客观检查交给脚本**。先复用已存在的入口。是否封装看输入输出、复用价值和漏检影响。需要判断和审美取舍的动作留给人和执行者。
5. **维持现状也是结论**。用最小动作解决问题，把真正需要用户决定的选项连同依据一起交付。

## 通用化与主动性

OPC 面向不同业务和项目，母版定义共同的目标、权限边界和可验证结果。复盘从具体案例提炼可复用的失败条件与验收信号，项目则保留自己的业务事实、工具选型和交付方式。

Agent 要对业务结果负责。在授权范围内，主动查清影响结果的事实，选择合适的工具和方法，处理可恢复的阻塞，并验证和呈现结果。目标或验收有多种会实质影响交付的解释时，先说明差异并给出建议，请有决策权的人拍板。其余可继续的工作照常推进。

例如，用户说「给我看」时，共同标准是让用户能看清变化并据此判断。前端可给可操作的预览，建模可用标注对比或动作演示，具体形式由任务决定。

## 七个经过试跑的反例

| 容易误判 | 实际要核对什么 |
| --- | --- |
| 看到执行者空闲就重发 | 核对任务卡、最后消息、工作树和真实报错。等待确认就转呈；仍在执行就先完成交接，避免重复写入。 |
| 工作区差异为空就判空转 | 已提交实现要比较基线与交付版本。只读任务核对引用和结论；视觉任务核对同版预览与截图。 |
| 每次咨询都摸清整个项目 | 先查足以改变本次结论的事实，位置不明或跨模块时再扩大。 |
| 只记产物路径就清理工作树 | 未入 Git 的正式产物先存到约定的持久位置，再由接收方打开核验。 |
| 专科人员探测工具就顺手改公共配置 | 专科人员提供探测和验证证据，由有权限的角色落盘公共工具栈与脚本。工具选型以实际可用的接口为准。 |
| 汇报把所有链接都放末尾 | 用户要看的预览、模型入口或对比图随结果展示。提交号、测试命令和追溯路径放在后面。 |
| 重复两次就强制脚本化 | 重复是评估信号。适合脚本的动作需要足够稳定且有复用或防漏检价值。随任务变化的视角仍由执行者决定。 |

接到真实反馈时，先查本机 CLI、配置和日志，验证问题究竟发生在哪里。例如窗口数量异常，应分清工具是否支持续聊和调度是否每次要求另开；专科工具可用性应对照具体工程的编译或渲染能力实测。评估外部方法时，先看团队规模、现有规则和实际失败路径，再拿可借的一步试跑。

## 演进闭环

1. **事实与增量**。找原始需求、任务卡和产物，回答实际遇到了什么、现行规则哪里覆盖、下次凭什么知道有效。
2. **最小提案**。只在证实缺口后提出改法。优先修订原规则，再考虑新增条款、项目 Skill 或确定性检查。达到正式提案条件时按角色规则完成独立复核。
3. **批准后核对四处生效点**。母版只发布通用内容，检查有无项目标识、机器路径或个人配置；受影响项目同步适用部分并遵守自身分支和推送约束；相关 Bot 更新本机入口和边界；配套任务卡与说明检查是否仍一致。真正需要改的地方才修改，并记录各处状态。
4. **成果式交付**。说明改动解决的问题、已验证的行为、待实测闭环和追溯链接。后续把实测证据和取舍更新到相应章节，避免文档只停留在首次交接。

## 留待下一次真实任务验证

- **视觉转呈**：执行者产出的同版预览或模型经协调者转呈后，用户能否从原会话直接看懂，并据此作决定。
- **专科工具链**：执行者给出实测证据，有权限的角色更新项目记录，下一张任务卡能否直接复用。
- **工具降级**：实时工具不可用时，离线路径能否生成符合约定的交付物，以及哪些实时检查仍待验证。
