# RESEARCH.md - 技术方案查证

重要决策要有证据。**证据不等于"GitHub 上 star 多的那个"。**

---

## 一、什么时候需要查证

需要：

- 选框架、库、中间件、云服务
- 定架构（单体/服务拆分、同步/异步、存储选型）
- 引入新的横切能力（认证、缓存、队列、监控、日志、权限）
- 改动对外契约或数据格式
- 性能、容量、成本有硬指标

不需要：

- 项目内已经有明确约定的事（按现有约定做）
- 纯实现细节、局部重构、bug 修复
- 只是在用已有的库/模式

不确定要不要查，就问一句："这个选择以后换掉贵不贵？"贵就查。

---

## 二、证据的优先级

从高到低。前一类能回答，就不要往下找：

1. **项目自身的代码、测试、基准数据、历史决策记录**
   最适合这个项目的证据，永远在项目里。
2. **官方文档、规范（RFC/W3C/IETF）、语言与框架的权威说明**
   接口行为、语义、兼容性，以官方为准。
3. **官方仓库的 issue/discussion、变更日志、安全公告**
   判断维护状态、已知缺陷、破坏性变更。
4. **成熟开源项目的实现与设计文档**
   看别人怎么解决同类问题，尤其是边界处理。
5. **基准测试、论文、行业报告**
   需要量化结论时用。
6. **博客、教程、问答**
   只作为线索来源，不作为结论依据。

GitHub 是第 3、4 类的常用载体，**不是唯一来源**。闭源、内网、离线项目
可能完全用不上它；此时官方文档与内部 ADR 就是主要证据。

---

## 三、评估一个开源项目

弱信号（只能作为参考，不能单独作为结论）：

- star 数、fork 数
- 提交频率
- 有没有测试目录

强信号（需要实际查看）：

- 最近的发版与破坏性变更节奏，是否与你的升级能力匹配
- issue 里同类问题的处理方式和响应质量
- 文档是否说明了边界条件和限制
- 测试是否真的覆盖核心路径（不是只有几个占位用例）
- 依赖树是否可控，有没有已知高危漏洞
- **许可证**是否与你的使用方式兼容
- 出问题时你能否自己修（代码可读性、体量）

经验判断：

- 库稳定、功能收敛后长期不更新，可能比频繁重构更安全。
- 小 star 数的项目可能在特定领域非常合适，不要因为数字直接排除。
- 大 star 数不能证明安全、性能或与你的场景适配。

## 四、对比做法

至少看 2 个候选方案（含"自己写一个最简版本"这个选项）。

对比维度：

| 维度 | 要回答的问题 |
|---|---|
| 适配度 | 覆盖需求的比例？有多少是为了用不上功能付代价？ |
| 复杂度 | 引入后团队要额外学多少？出问题谁来修？ |
| 性能 | 有基准数据吗？在你的数据规模下还成立吗？ |
| 依赖与体积 | 增加多少依赖？会不会污染全局？ |
| 退出成本 | 以后换掉要改多少代码？数据能迁走吗？ |
| 维护与许可 | 谁在维护？许可允许你的用法吗？ |
| 安全 | 有已知漏洞吗？攻击面变大了吗？ |

结论要能回答："为什么不选另一个。" 答不上来，说明还没比清楚。

## 五、记录

需要留痕的决策写进项目自己的决策记录（例如 `docs/decisions.md`）。
最小字段：

```markdown
## YYYY-MM-DD 决策标题

- 背景：要解决什么问题，约束是什么
- 选项：A / B / 自研最简版，各自代价
- 决定：选哪个
- 理由：关键的一两条，不是全部理由的堆砌
- 证据：链接或命令输出（官方文档、基准、issue、压测结果）
- 代价：接受了什么缺点
- 复核条件：什么情况下需要重新评估
```

约束：

- 证据写链接和版本号，不要只写"参考了某文章"。
- 没查到的部分标注为推测，不要写成已确认。
- 决策被推翻时，保留原记录，追加新记录说明为什么改。

## 六、常见错误

- 只看 star 数就选型
- 把"能跑 demo"当成"适合生产"
- 没在自己的数据规模上验证性能
- 忽略许可证与合规要求
- 引入一个重框架解决一个能用 30 行解决的问题
- 用二手教程的结论覆盖官方文档
- 决策不记录，三个月后没人知道为什么这么选
