# PRINCIPLES.md - 编码原则

四条原则，加一份"什么时候可以偏离"的判定方式。

原则描述的是**默认做法**，不是绝对禁令。偏离需要理由，理由要能被别人复核。

---

## 原则 1：Think Before Coding

**先把问题说清楚，再写第一行代码。**

具体要求：

- **不假设。** 需求、数据形态、外部接口、运行环境不确定时，先问或先查，不要用"应该是这样"继续往下写。
- **不隐瞒困惑。** 看不懂的旧代码、互相矛盾的文档、跑不通的命令，明确说出来，不要绕过去假装理解。
- **表面化权衡。** 有多种做法时，列出各自的代价（复杂度、性能、可维护性、迁移成本），再选一个。
- **区分事实与推测。** 结论要么来自读过的代码、跑过的命令、查到的文档，要么明确标注为推测。

**动手前的三个问题：**

1. 我要改的行为，现在的实际行为是什么？（读过代码/跑过测试才能回答）
2. 这次改动的边界在哪？哪些文件属于本次范围，哪些不属于？
3. 改完怎么证明它好了？命令是什么，预期输出是什么？

如果第 3 个问题答不出来，说明还没准备好改。

---

## 原则 2：Simplicity First

**能解决问题的最小实现。没有推测性的设计。**

默认不做：

- 需求里没有的功能、开关、配置项
- 只有一处调用的抽象层
- 为"以后可能换实现"预留的接口
- 为几乎不可能发生的场景堆叠的防御分支
- 为了套用设计模式而增加的间接层

**判断是否过度设计的三个问题：**

1. 删掉这段代码，当前需求还能满足吗？能 → 删掉。
2. 这个分支在真实输入下会发生吗？没有证据 → 先别写，问清楚。
3. 这个抽象有几个调用方？只有一个 → 就近内联。

### 校验放在信任边界上

"只校验一次"容易被误读成"内部一律不校验"。正确的边界是：

- **同一份已校验的可信数据**在内部流转时，不要层层重复判空、判格式、判范围。
- **跨越信任边界时必须校验**：HTTP/RPC 入口、消息队列消费、文件与命令行输入、
  第三方回调、插件、跨租户访问、写入持久化之前。
- 涉及**权限、租户隔离、金额、审计**的不变量，不因为"上游已经查过"就跳过。
- 客户端校验只改善体验，**不能替代服务端校验**。

### 低概率防御先说清楚

要为一个罕见场景加保护，先说明：触发条件、发生概率、失败后果、这段代码的复杂度代价。
得到确认再加。没有确认就写，属于擅自扩大范围。

### 异常与错误处理跟随项目

- 优先沿用项目现有的错误处理方式。项目用异常就用异常，项目用结果类型就用结果类型。
- 结果类型（`Result` / `Option` / 错误返回值）在**错误是预期分支**、需要显式分支处理时更清楚。
- 异常机制在**资源清理、事务回滚、取消传播**上仍不可替代。有事务边界的地方，
  不要为了统一风格把异常改成返回值而丢掉回滚语义。
- 捕获异常只做三件事之一：处理、转换并加上下文、向上抛。**不允许静默吞掉。**

### 函数的粒度

单个函数能讲清楚的事，不要拆成三层调用。但以下情况拆开是合理的，不算过度设计：

- 需要单独测试的纯逻辑
- 需要独立事务边界或权限检查的步骤
- 拆开后明显更容易读（而不是更难跟）

行数不是指标。"200 行能写成 50 行"是提醒去找重复和冗余，不是硬门槛。

## 原则 3：Surgical Changes

**只改必需的部分，只清理自己造成的问题。**

- 每改一行，都能回答"这一行对应哪个需求"。
- 匹配周围代码的风格、命名、目录习惯，即使你更喜欢另一种写法。
- 不顺手重排 import、不顺手改引号、不顺手统一格式、不顺手升级依赖。
- 发现无关的坏味道：记下来告诉用户，不要在这个改动里修。
- 自己引入的临时调试代码、注释掉的旧代码、无用文件，在提交前清掉。
- 需要跨文件重构才能完成需求时，先说明这是重构，取得同意后再做。

**例外：** 如果不动相邻代码就无法完成需求（例如必须改函数签名），
把这类连带改动在方案里单独列出，让用户知道范围扩大了。

---

## 原则 4：Goal-Driven Execution

**先定义成功标准，再用验证闭环收尾。**

一次改动开始前写下（哪怕是对话里一句话）：

- 目标行为：改完之后，什么输入产生什么输出
- 验证方式：跑哪个命令、看哪个日志、点哪个页面
- 不做什么：这次明确排除的范围

完成后：

- 跑验证，贴出真实结果，而不是"应该没问题"。
- 验证失败就继续修，不要改验证标准来迁就实现。
- 如果只验证了一部分（例如只测了正常路径），明确说明哪部分没验证。

**验证分层**（命令由各项目在自己的 `AGENTS.md` 里定义）：

| 层级 | 内容 | 什么时候跑 |
|---|---|---|
| 快测 | 编译/类型检查/lint + 与改动相关的单测 | 每次改完 |
| 门禁 | 全量测试、构建、静态检查 | 合并主干前、交付前 |
| 重测 | E2E、集成、性能、打包冒烟 | 阶段收尾、发布前 |

编码途中只跑秒级检查，不要每改两行就跑全量测试；但**没有跑过快测的改动不算完成**。

## 什么时候可以偏离原则

以下情况允许偏离，但必须同时满足三条：**说明理由、限定范围、能被复核**。

| 场景 | 允许的偏离 | 必须附带 |
|---|---|---|
| 性能关键路径 | 更复杂的实现、手工优化 | 基准数据（改前/改后） |
| 强监管/安全关键 | 冗余校验、双人复核、额外日志 | 对应规范条款 |
| 兼容历史数据/接口 | 保留旧分支与兼容层 | 清理条件与时间点 |
| 已有技术债 | 保留现有复杂逻辑 | 在代码注释里写明原因 |

不允许作为偏离理由的说法：

- "以后可能需要"
- "万一出现某种情况"
- "这样写更舒服/更漂亮"
- "业界都这么写"（没有具体证据）

偏离的声明写在**项目自己的 `AGENTS.md`** 里，写清范围（整个项目 / 某模块 / 某文件）。
未被声明覆盖的部分，仍然按默认原则执行。

## 自查清单

改动前：

- [ ] 我知道现在的实际行为，不是猜的
- [ ] 我说清了这次的范围和不做的事
- [ ] 我知道用什么命令验证

改动后：

- [ ] 没有超出需求的功能或抽象
- [ ] 新增的防御有明确触发条件和确认
- [ ] 校验放在了正确的信任边界
- [ ] 没有顺手改无关代码
- [ ] 快测通过，结果是我亲眼看到的
- [ ] 没验证的部分，我说清楚了
