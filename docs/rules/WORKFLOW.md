# WORKFLOW.md - 改动分级与权限边界

按**风险**决定流程，不按行数。行数只用来估工作量。

---

## 一、先看危险特征，再定等级

以下任意一条成立，直接升到对应等级；同时符合多个时，**取最高等级**。

| 特征 | 最低等级 |
|---|---|
| 认证、授权、会话、加密、密钥 | 红灯 |
| 支付、计费、资金、发票 | 红灯 |
| 数据迁移、结构变更、批量改数据、删数据 | 红灯 |
| 发布流程、CI/CD、基础设施、生产配置 | 红灯 |
| 对外接口契约、公开 API、SDK 兼容性 | 红灯 |
| 不可逆操作（git 历史、存储桶、域名、证书） | 红灯 |
| 跨服务/跨仓库改动、含数据回填 | 红灯 |
| 新依赖、新外部服务、新权限 | 黄灯 |
| 影响多个模块的行为变化 | 黄灯 |
| 性能优化（无基准数据时） | 黄灯 |
| 只改文档、注释、文案 | 绿灯 |
| 只改格式、局部小修、可逆且不碰接口与数据 | 绿灯 |
| 需要先探明现状才能判断 | 先只读探查，再定级 |

规模与不确定性只在同级内调整方式：改动越大、越不确定，方案和验证就要越细。

---

## 二、三个等级

### 绿灯：直接做

**典型：** typo、文案、日志措辞、单点小 bug（原因已定位）、局部样式、纯文档。

**做法：**

1. 确认改动范围（哪几个文件）
2. 改
3. 跑快测
4. 一句话说明改了什么、验证结果是什么

**不需要**方案评审，也**不需要**停下来等确认。但如果发现实际范围比预想大，
或碰到高风险目录，立刻停下来重新定级。

### 黄灯：先给短方案，再动手

**典型：** 新增功能模块、重构局部结构、加依赖、改现有模块的关键逻辑、性能优化。

**做法：**

1. 只读摸清现状（相关调用链、可复用的现成组件、真实测试命令）
2. 给出短方案：改哪里、复用什么、不做什么、怎么验证、有哪些取舍
3. **等用户确认方案**
4. 在分支上实现，跑快测
5. 交付时说明改动清单、验证结果、遗留问题
6. 需要合并时，走第九节的合并规则

方案控制在能读懂的长度。小功能几段话即可，不要为两行改动写设计文档。

### 红灯：完整方案 + 分步确认

**典型：** 上面表格里的全部高危项，以及跨系统重构、不可逆操作。

**做法：**

1. 只读摸清现状，列出受影响面（调用方、数据、配置、下游）
2. 完整方案，必须包含：
   - 现状与目标行为
   - 改动清单（文件级）
   - 数据与兼容性影响
   - **回滚办法**（不能只写"回滚代码"）
   - 验证计划（快测 / 门禁 / 重测各跑什么）
   - 不做的范围
3. **等用户确认方案**
4. **关键动作逐个确认**：改表结构、跑迁移、删数据、切换开关、发布、合并主干
5. 分阶段实施，每阶段结束跑对应验证并汇报
6. 出问题时优先止损和回滚，不要在故障中顺手重构

## 三、授权边界

**同意方案 ≠ 同意执行到底。** 这是最容易出事的地方，单独列清楚：

| 动作 | 需要什么授权 |
|---|---|
| 改代码、加测试、改文档（范围内） | 方案确认后即可 |
| 装/升级依赖、改构建配置 | 单独确认 |
| 提交到分支、推送分支 | 方案确认后默认允许，以项目约定为准 |
| **合并主干** | **单独确认**（每次合并都要） |
| 改数据库结构、跑迁移、回填 | 单独确认，每个动作 |
| 删除数据、删除文件、清理历史 | 单独确认，说明恢复方式 |
| 发布、部署、改生产配置 | 单独确认，说明回滚方式 |
| 动凭证、密钥、权限策略 | 单独确认 |
| 对外发送内容（PR 描述、公告、邮件） | 单独确认 |

默认行为：**能做到，但没被授权，就不做。** 不要用"顺手"或"为了完整性"绕过。

如果项目要求自动化（例如 CI 自动合并），那属于项目自己的策略，
必须在项目 `AGENTS.md` 里写清楚，不能由 AI 自行推断。

---

## 四、方案该写多细

| 等级 | 方案形态 | 长度参考 |
|---|---|---|
| 绿灯 | 不写方案，一句话说明 | — |
| 黄灯 | 对话里的短方案 | 5–15 行 |
| 红灯 | 落盘的方案文档或长消息 | 按风险，不设上限 |

方案必须让人看懂**外部行为变化**，而不是堆实现细节。判断标准：
一个不熟悉这段代码的同事读完，能说出"改完会怎样、风险在哪、怎么验证"。

---

## 五、验证

验证分三层（定义见 [PRINCIPLES.md](PRINCIPLES.md#原则-4goal-driven-execution)）：
快测、门禁、重测。

各等级的最低要求：

| 等级 | 快测 | 门禁 | 重测 |
|---|---|---|---|
| 绿灯 | 必跑 | 合并前跑 | 不需要 |
| 黄灯 | 必跑 | 合并前跑 | 涉及关键路径时跑 |
| 红灯 | 必跑 | 必跑 | 必跑，且记录结果 |

补充规则：

- 命令以项目 `AGENTS.md` 为准。项目没写，就先问，不要自己编一个"看起来对"的命令。
- 测试失败时，先判断是改动引入的还是原本就红。原本就红的，说明清楚，不要假装通过。
- 不能自动化验证的部分（UI、硬件、第三方环境），写出人工复核步骤，并说明谁做。

## 六、改动被卡住时

- **发现信息不足**：停下来问，不要用假设硬推。
- **发现范围扩大**：停下来重新定级，说明为什么变大。
- **发现方案有错**：停下来改方案，不要在实现里绕过去。
- **发现已有代码本身就是错的**：记录，单独提出来，不要顺手一起改。
- **验证无法通过且原因不明**：保留现场（分支、日志、复现步骤），报告，不要反复试错刷屏。

---

## 七、无 Git / 无测试的项目

本流程默认有版本控制和自动化测试。缺这两样的项目需要降级适配：

- 无版本控制：动手前先做可回退的备份，并说明备份位置。这是临时措施，不是长期方案。
- 无自动化测试：每个改动都要写出手工验证步骤和预期结果，并实际执行一次。
- 两者都没有：默认全部按**红灯**处理，且不接无人监督的批量改动。

## 八、AI 自主性范围

| 可以做 | 不可以做 |
|---|---|
| 只读探查代码、跑只读命令 | 未经授权改主干、发布、删数据 |
| 在授权范围内改代码并跑快测 | 超出方案范围顺手改别的 |
| 提出方案、指出风险和替代方案 | 替用户拍板不可逆的取舍 |
| 报告验证结果，包括失败 | 把没验证的说成已验证 |
| 发现规范与项目冲突并提出 | 静默忽略冲突继续干 |

## 九、合并规则

合并主干是独立动作，任何等级都不例外：

1. 确认当前分支、目标分支、将要合并的提交
2. 确认工作区干净、没有未提交的调试代码
3. 跑门禁
4. **向用户报告**：改了什么、验证结果、遗留问题、目标分支
5. 得到确认后再合并
6. 合并后确认主分支状态，报告实际结果（包括冲突处理方式）

多个分支并行时，说明每个分支的用途和归属，不要合并来路不明的分支。

## 十、快速自查

动手前：

- [ ] 定级了吗？取的是最高等级吗？
- [ ] 有没有踩到红灯特征？
- [ ] 现状是查过的还是猜的？
- [ ] 验证命令确定吗？

交付前：

- [ ] 对照约定核过实际改动。若改到共用代码，列出可能受影响的其他用法，并说明承诺保留的行为哪些已验证、哪些仍待验证。
- [ ] 快测/门禁/重测按等级跑过
- [ ] 需要单独确认的动作，确认了吗？
- [ ] 没验证的部分说明了吗？
- [ ] 文档只改了权威出处
