# 项目级 Skill 管理总表（SKILLS.md）

> 维护者：GM。本文件记录本项目实际安装和验证过的 Skill，解耦**角色（谁负责）**、**Skill（需要什么能力）**与**执行器（Claude Code / Codex / Antigravity / OpenCode 等）**。
> 存放原则：所有 Skill 统一扁平存放在项目根目录 `skills/<技能名>/SKILL.md`（一项 Skill 全项目只存一份，不按角色建子目录；适用角色在本表标记）。规则冲突时一律以 `AGENTS.md` 为准。

## 2. 调研、安装与验收纪律
1. **找 Skill（GM 调研汇报）**：老板要求寻找某类 Skill 时，先查本表；缺项再调研 2~3 个候选，逐个说明：**能产出什么、怎么调用、来源仓库、最近维护状态、开源许可证、运行依赖**（如报 GitHub stars，须标明统计日期，并说明是整仓还是单 Skill）。
2. **装 Skill（黄/红灯审批 + 分支实测）**：
   - 安装外部 Skill 视同引入新依赖（黄灯）；若附带可执行脚本、外部权限或凭证，按实际操作定级并由 L1 审查脚本安全。
   - 经老板确认后，固定版本装入当前项目的任务分支 `skills/<技能名>/`（连同随附脚本、模板与资源）并登记本表。
   - **验收标准不是“安装成功”，而是在新 Worktree 里实际调用一次并产出约定结果**（如生成一个可打开的模板页），通过后按 `AGENTS.md` 合并规则合入主分支。
3. **跨执行器验证与接力**：
   - 严禁假设“所有执行器读到 `SKILL.md` 就一定生效”。哪个执行器实测跑通过，就在上表“各执行器实测状态”记一笔（如 `Claude Code 已验证`、`Antigravity 浏览器截图已验证`）。
   - 若执行器缺外部工具（例如能生成页面但无法截浏览器图），由 GM 把验证步骤接力给具备浏览器能力的执行器完成；**交接时必须在任务卡第 5 节（绿灯免卡任务则在派单会话中）写明当前工作树路径、预览地址、要验证的页面，以及对应提交号（若尚未提交，须明确注明使用当前工作树正在运行的预览）**，防止验收方误看主分支旧页面。
4. **交互型 Skill 的确认点保护（严禁 GM 静默跳过，同时尊重 AI 判断）**：
   - 登记自带“动手前确认/询问”机制的 Skill（如 UI 设计、原型探索类）时，须在上表写明其**会改变方向的必填输入与确认点**。
   - **已有明确结论就沿用，老板授权自定的部分由执行者发挥；只有缺失信息会改变交付物时才集中询问；需要看东西才能决定时，先交方向摘要、可交互样稿或对比图，再等老板选择。**
   - 派发这类 Skill 时，GM 不得替老板猜测后直接写“做到底”，须在任务卡标明“已前置澄清”或“停在 Skill 确认点”；执行者发现卡中缺会改变交付物的关键项且未授权自定时，应先向 GM 集中追问 1 次，不得硬猜。
5. **恢复与跨项目复用**：
   - 已提交的 Skill 丢失时，直接用 `git checkout` 或按上表“来源与固定版本”重装。
   - **不自动同步进母版**：某个 Skill 在第二个项目也证实可复用、且核对过**开源许可证允许再分发**后，再经老板确认升入 `opc-workflow` 母版；项目特有 Skill 仅留在各自仓库。
